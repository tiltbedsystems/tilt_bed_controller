## b. Design as built

No new plan document was produced — this session implemented a design supplied
in full by the reviewer. What follows is the design **as actually built**,
including the places where the implementation had to make a call the spec did
not cover. The canonical record is `DECISIONS.md` #33, added in `83cc628`.

### b.1 A build-system constraint that shaped the whole thing

The spec asked for a "new sampler". **A new `.c` file was not possible.**
`cmake_gcc/tilt_bed_controller_project.cmake` lists application sources
explicitly and is generated by Simplicity Studio from the `.slcp`; adding a
file means either hand-editing a generated file — forbidden by this repo's
hard constraints — or a configurator round-trip by the user.

So the sampler lives in **`auto_level.c`**, which is also where `read_accel()`
and the filter already are. This is defensible on its own terms (it is the
accelerometer module) but it does put the two tilt chains in one file, which
makes DECISIONS #31's storage separation *more* important to state loudly, not
less. The state struct, the two named instances, and the comment block above
the sampler are all doing that work. If the reviewer would rather have a
`tilt_telemetry.c`, that is a configurator task for the user, not something
this session could do.

### b.2 One window, four triggers

Implemented exactly as specified. The window is open when **a motor is
energised OR the burst timer is running**; while open, the sampler runs on
every main-loop pass.

| | Trigger | Where |
|---|---|---|
| T1 | subscriber count 0 → 1 | `update_status_subscriber_count()`, `ble_bed_service.c` |
| T2 | `REFRESH_TILT` arrives | `process_pending_command()`, main-loop context |
| T3 | motors any-on → all-off | `tilt_telemetry_tick()`, `auto_level.c` |
| T4 | auto-level | nothing added |

Arming is `sl_sleeptimer_restart_timer()`, which is precisely "extend, don't
stack": an already-running burst has its expiry pushed out to a full
`TILT_TELEMETRY_BURST_MS` from now, and there is only ever one timer.

**Nothing interrupts anything.** Arming sets a timer and returns. There is no
call into the motion path from the sampler, and no call into the sampler from
the motion path other than arming. A movement starting mid-burst keeps the
window open; T3 re-arms on release.

### b.3 Two ordering decisions the spec did not pin down

Both are visible in the diff and both are deliberate.

**1. The T3 edge is tracked before the subscriber gate; the T3 *arm* is after
it.** If the edge were tracked after the gate, `tilt_prev_motors_on` would go
stale whenever nothing was subscribed, and a phone subscribing mid-move would
see a spurious "motors just stopped" edge on its first tick. If the arm were
before the gate, a phone-less bed would veto sleep for 500 ms after every
switch move — a behaviour change on exactly the configuration that is supposed
to stay bit-for-bit identical. Splitting them satisfies both.

**2. `process_pending_command()` is drained *before* `ble_bed_service_tick()`'s
subscriber early-return.** A Command write is valid from any bonded
connection whether or not it subscribed to Bed Status, and its Command Result
must still be sent. Only the telemetry notify is subscriber-gated. Had the
drain gone after the early-return, a client that wrote without subscribing
would get silence, which is the failure mode item 11 of the spec exists to
prevent.

### b.4 The `read_accel()` split, and why auto-level's numbers are unchanged

The spec required telemetry to own its filter state, including LPF state. The
LPF lived inside `read_accel()`, writing file-scope globals — so calling
`read_accel()` from telemetry would have written auto-level's LPF accumulator,
which #31 forbids.

`read_accel()` was therefore split: it now produces `latest_*_scaled` and
stops. The LPF moved into `accel_filter_update(accel_filter_state_t *st)`,
which filters into the caller's own accumulator and then runs the caller's
own circular buffer.

**Equivalence argument for auto-level** (this is the part that matters, since
it is the safety path):

| Before | After |
|---|---|
| `read_accel()`: sample → angles → scaled → LPF into `latest_*_filtered` | `read_accel()`: sample → angles → scaled |
| `accel_running_average()`: reads `latest_*_filtered`, updates buffer/sums/index, computes averages, subtracts baseline | `accel_filter_update(&auto_level_filter)`: LPF into `st->lpf_*`, then the identical buffer/sums/index/average/baseline arithmetic on `st` |
| — | `accel_running_average()` mirrors `st`'s outputs into the same globals |

The arithmetic, its order, and the per-pass call rate are unchanged. Every
value auto-level acts on is computed from the same inputs in the same sequence.
`auto_level_filter` is zero-initialised exactly as the globals were. The only
observable difference is that the numbers now live in a struct before being
copied to the globals every existing reader still uses.

This is the one part of the change that touches the auto-level path, and it is
a mechanical transcription. It is also, honestly, the highest-risk edit in the
diff — see §f.1.

### b.5 Filter: shared algorithm, separate storage

`accel_filter_state_t` holds `readings_roll[130]`, `readings_pitch[130]`,
`sum_roll`, `sum_pitch`, `index`, `lpf_roll`, `lpf_pitch`, and the outputs.
Two instances: `auto_level_filter` and `telemetry_filter`. The shared function
takes a pointer. Telemetry writes nothing of auto-level's — that is checkable
by grep: `auto_level_filter` appears only inside `accel_running_average()`.

Because the algorithm and the per-pass rate are identical, the telemetry value
has the same ~300 ms averaging window and the same on-screen smoothness as
auto-level's. That is what closes DECISIONS #32.

### b.6 Burst duration and sleep

`TILT_TELEMETRY_BURST_MS = 500`, in milliseconds via sleeptimer (#2), never
loop passes (#29). At the measured ~2.31 ms/pass that is ~200 passes against a
130-slot filter. Commented as bench-tunable with the trade-off stated: longer
gives the filter more convergence margin and the frame more time to stop
rocking; shorter risks freezing the display before the bed has settled, which
defeats T3 entirely.

`app_is_ok_to_sleep()` vetoes sleep while the burst runs. Bounded by the
burst, and unreachable unless a phone is subscribed.

### b.7 Tilt source selection

`bed_status.c` now picks explicitly, with the reasoning inline:

- auto-level or settings mode running → **auto-level's** value (it owns the
  accelerometer, telemetry has stood down, and it is the value auto-level is
  steering on);
- otherwise, once telemetry has ever produced a value → **telemetry's**;
- otherwise → auto-level's last-known, which is the pre-change behaviour.

Both chains are in the internal sign convention, so the single wire negation
added in `140c37b` still applies to whichever was selected — the "only place
the two conventions meet" property is preserved.

### b.8 `tilt_fresh`

Untouched. Still hardcoded `false` at the `ble_bed_service_encode_status()`
call site. The flags byte is not modified anywhere in this change. Between
bursts the value genuinely is stale, so 0 stays honest and the app's
`TODO(tilt-fresh)` ungating stays correct.

### b.9 Command write path

First write handler in the firmware. One opcode.

- **Callback does nothing but copy.** Four bytes into a static buffer, the
  connection handle, the length **as written** (not clamped, so a wrong-length
  write can be rejected rather than silently padded), a flag, return.
- **All decisions in `process_pending_command()`**, called from
  `ble_bed_service_tick()` in main-loop context.
- `REFRESH_TILT` (0x07) with `arg0 == 0 && arg1 == 0 && len == 4` → arm the
  burst, notify `{ seq, 0x00 }`.
- Anything else — unknown opcode, any of 0x01–0x06, wrong length, non-zero
  args → notify `{ seq, 0x04 }`. A short write has no trustworthy `seq`, so 0
  is echoed rather than a byte that was never sent.
- Accepted from **either role** and **in settings mode**, per the ruling.

Verified against the SDK header rather than assumed: `sl_bt_evt_gatt_server_attribute_value_t`
has `connection`, `attribute`, `att_opcode`, `offset`, `value` — see §d.4.

**One known limitation, deliberately left in.** Only one write is buffered; a
second arriving before the tick drains the first overwrites it. Harmless while
REFRESH_TILT is the only opcode — two refreshes and one refresh are the same
thing, and bursts extend rather than stack — but it **must** be revisited
before MOVE_START, whose 100 ms repeat cadence and dead-man semantics make a
dropped write matter. Commented at the function and raised in §f.

## f. QUESTIONS FOR REVIEW

1. **The `read_accel()` split is the riskiest edit here and it is in the
   safety path.** It was forced: telemetry needs its own LPF accumulator, the
   LPF lived inside `read_accel()`, and #31 forbids writing auto-level's. The
   alternative was duplicating the filter, which drifts. I took the
   transcription (§b.4) and argued equivalence, but this is the one hunk worth
   reading line-by-line against the original.
2. **Should collision re-verification gate the rest of the acceptance run?**
   §5 is listed as a step, but the loop rate changing on the manual-move path
   is a change in collision behaviour, and the collision test is the only one
   that can hurt someone. My instinct is to run the loop-rate measurement and
   §5 *first*, before the long soaks, and stop if §5 regresses. The step order
   below reflects that. Confirm.
3. **The sampler lives in `auto_level.c`** because of §b.1. If a separate
   `tilt_telemetry.c` is wanted, it needs a configurator round-trip — a user
   task. Worth doing now or later?
4. **Single-slot command buffering** is documented and harmless for
   REFRESH_TILT but is a real limitation for MOVE_START. Should a small ring
   buffer land with the next opcode, or now while the path is being reviewed?
5. **`bed_status.c` gained `#include "app.h"` and `#include "settings_mode.h"`**
   for `auto_level_active` / `in_settings_mode`. That widens what was a fairly
   self-contained snapshot module. The alternative was inferring the state
   from `out->command` and `out->in_settings_mode`, which are proxies rather
   than the actual flags the sampler is gated on. I preferred the direct
   read; say if you would rather have the proxy and fewer includes.
6. **Settings mode gates the sampler off entirely**, not just during the
   zero-level capture. Simpler and strictly more conservative, but it means
   tilt is frozen for the whole time the user is in settings mode. Acceptable?

### Step 1 — the BEFORE loop-rate measurement (do this FIRST, on the OLD firmware)

This has to happen **before** you flash the new firmware, or the number is
gone. `~2.31 ms/pass` is the only loop-rate figure that exists and it was
measured on the **auto-level** path. DECISIONS #29 exists specifically to stop
that number being reused for a different path. The manual-move path has never
been measured, so we need both a before and an after.

Build and flash the **previous** commit:

```
git checkout 23b84aa
```

Build it however you normally do (VS Code CMake build), flash it, then:

```
git checkout main
```

so your working tree is back on the new code. (Checking out an old commit
prints a "detached HEAD" warning — that is normal and the second command undoes
it.)

To take the measurement you need a pass counter printing over the UART.
**There is no such counter in the firmware right now** — the instrumentation
from the DECISIONS #30 bisection was stripped when that work finished. So this
step needs a small temporary edit before each build:

In `app.c`, at the very end of `app_process_action()`, temporarily add:

```c
  {
    static uint32_t passes = 0;
    static uint32_t last_report_tick = 0;
    passes++;
    uint32_t now = sl_sleeptimer_get_tick_count();
    if (sl_sleeptimer_tick_to_ms(now - last_report_tick) >= 1000) {
      printf("LOOPRATE %lu passes/sec\r\n", (unsigned long)passes);
      passes = 0;
      last_report_tick = now;
    }
  }
```

Then:

1. Open PuTTY on **COM6**, and turn on logging: Session → Logging → "All
   session output", set a filename like `looprate_before.log`.
2. Power the bed up and let it sit still. Note the idle `LOOPRATE` number.
3. **Hold one side button (say UP LEFT) for a full 10 seconds** while the
   motors run. Note the `LOOPRATE` numbers during the move — that is the
   manual-move figure, the one that has never existed before.
4. Release. Save the log.

Write down: idle passes/sec, and moving passes/sec.

Remove the temporary block, or keep it for step 2 and remove it after — but
**do not commit it**.

### Step 2 — the AFTER measurement

Same thing on the new firmware. Build and flash `main` (`83cc628`) with the
same temporary counter block added, log to `looprate_after.log`, repeat the
same 10-second hold on the same button.

Compare:

- **Idle, no phone connected:** should be essentially identical to before. If
  it is not, the subscriber gate is not doing its job and that is a bug —
  stop and report it.
- **Moving, no phone connected:** should also be essentially identical, for
  the same reason.
- **Moving, phone connected and subscribed:** this is the one expected to drop.
  Write the number down. It feeds step 3.

### Step 3 — collision detection, on a manual move (REGRESSION.md §5)

**Do this before the long soaks.** Collision timing is calibrated in loop
passes, so the number you just measured changing *is* a change in collision
behaviour. This is the one test in this change that could hurt someone.

With the phone connected and subscribed:

1. Put the rigid block in place and raise one side into it. Motors should stop,
   all LEDs blink 3 cycles, motors briefly reverse starting at blink 2, then
   everything stops.
2. Lower one side onto the block. Same trip sequence.
3. Soft obstruction (pillow) while raising — confirm it still trips, even if
   slower.
4. Compare how hard/fast it trips against your memory of the pre-change
   behaviour. If it feels noticeably later or takes noticeably more force,
   **stop and report it** — do not continue to the soaks.

### Step 4 — (a) fresh tilt on connect

1. Move the bed with the wall switch so it is definitely off-level, then leave
   it still for a minute or two.
2. Force-close the app so it fully disconnects.
3. Re-open the app and connect.

**Expect:** the tilt readout updates to the bed's actual current angle within
about a second of connecting. **Fail:** it shows a value left over from the
last auto-level run and never changes.

### Step 5 — (b) live tilt during a manual move

With the app connected and showing tilt:

1. Hold UP HEAD for several seconds. Watch the phone.
2. Repeat for UP LEFT, UP RIGHT, UP FOOT, and UP ALL / DOWN ALL.

**Expect:** roll and pitch update continuously the whole time the motors run,
not just at the start and end.

### Step 6 — (c) the settle

1. Hold a side button for ~5 seconds, then release, and **keep watching the
   phone for the next 2 seconds.**

**Expect:** the number keeps moving for roughly half a second after the motors
stop, then comes to rest. That drift is the frame settling and it is the whole
point of trigger T3. **Fail:** the number freezes the instant the motors stop.

### Step 7 — (d) the refresh command

The app's refresh button does not exist yet (PROMPT G). Until it does, use nRF
Connect on the phone:

1. Connect and bond to the bed in nRF Connect.
2. Find the service `54b10000-ef39-4f03-a91d-eb12b0d067c9`.
3. Find characteristic `54b10001-...` — that is Command.
4. Also enable notifications on `54b10002-...` — that is Command Result, so you
   can see the reply.
5. Write these four bytes to Command, as hex: `07 00 00 01`
   (opcode 0x07, arg0 0, arg1 0, seq 1).

**Expect:** Command Result notifies `01 00` — your seq echoed back, and 0x00
meaning ACCEPTED. Tilt on the Bed Status characteristic refreshes. **Nothing
moves.**

Then test rejection — write `01 04 01 02` (MOVE_START, which is not
implemented):

**Expect:** Command Result notifies `02 04` — seq 2, result 0x04
REJECTED_INVALID. **Nothing moves.** If any motor so much as twitches, stop
everything and report it.

Also try `07 01 00 03` (REFRESH_TILT with a non-zero arg):

**Expect:** `03 04` — rejected, because both args must be zero.

### Step 8 — (e) movement during a burst

1. Write `07 00 00 04` to Command (or press refresh, once it exists).
2. **Immediately** — within half a second — press and hold a movement button.

**Expect:** the bed moves normally and immediately. Tilt keeps updating. The
burst does not block, delay, or cancel the movement, and the movement does not
cancel the burst.

### Step 9 — the full regression

Run all of `docs/REGRESSION.md` with the phone bonded and subscribed to Bed
Status **for the entire run**, into a new copy of the record. Two parts matter
most here:

- **§6.8, sustained auto-level with the phone subscribed.** This is the check
  that caught DECISIONS #26 and #30. Do not shorten it — a quick or near-level
  run is not sufficient coverage.
- **Sustained manual move on each side and ALL, held to the physical limit,**
  watching the UART for `connection_closed ... reason=0x1008`. That is the
  supervision-timeout signature. Any occurrence means stop and report.

Save the PuTTY log with the record.
